# 1. A workflow now, an agent as a later layer

Status: accepted · 2026-11-12

## Context

The tool reviews dbt model changes in CI. There are two ways to use an LLM for that.

**Workflow.** Code decides what to look at. Deterministic rules run first. For the judgement calls a rule cannot make
(does this join multiply rows?), code assembles the context and makes one LLM call per changed model, with a fixed
rubric and a fixed output schema. The LLM has no tools.

**Agent.** An LLM with tools is given the pull request and the whole repository and decides for itself what to open,
what to run and what to report.

## What each one buys

| | Workflow | Agent |
|---|---|---|
| Finds problems nobody wrote a check for | No | Yes |
| Can fetch context nobody thought to supply | No | Yes: any file, several steps of lineage, `dbt compile` |
| Cost and time per pull request | One short call per changed model | Many calls, minutes |
| Same input, same output | Nearly; rules exactly | No |
| Testable without a model | Yes: the LLM is one function that can be faked | Hard |
| What an instruction hidden in a pull request can do | Suppress an LLM finding | Whatever the tools allow |

A pull request is untrusted text. The workflow's LLM can only return findings, and only rules can fail the build, so
the worst case of a successful prompt injection is a missed warning.

## Decision

Build the workflow. It is the right shape for a check that runs on every pull request and may block a merge: cheap,
fast, predictable and measurable.

The LLM judges only the categories in the rubric, on context chosen for each. It does not explore. That is the limit
of this design, stated plainly: **it finds what we thought to look for.**

## Consequences

- A new kind of problem needs a new rule or rubric entry before the tool can see it.
- The scenario set (`examples/`) is the measure of whether a change to a rule or to the prompt helped.
- The LLM check is one function from context to findings. Something else can sit behind it later, including an agent,
  while the output schema, the validation of findings and the scenarios stay.

## The agent layer, when it comes

An agent is how the blind spots of the workflow get found. It is added as a layer on top, never as the gate. Options,
roughly in the order worth trying:

1. **Shadow mode.** Run the agent next to the checks at first. A problem the agent finds and the checks miss
   becomes a scenario, then a rubric entry, then a rule if it can be made deterministic.
2. **Risk tiers.** Run the agent only where a mistake is expensive: models with many downstream dependents, models
   that feed finance reporting, incremental models, macros.
3. **Escalation.** Hand the agent what the workflow cannot see: SQL generated by macros, or a file that failed to
   parse.

The Claude Code team describes the same layering for their own code review: deterministic CI always blocks, the
depth of review is set by the risk of the change, and every past incident becomes a case in an eval set
([How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/), 2026-10-15).

Because it reads untrusted code, the agent gets read-only tools, no network and no secrets. It has a budget and a
turn limit, the scenario set measures it like the workflow, and its findings never fail the build.
